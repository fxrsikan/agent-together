# 对比实验：Agent Together 到底有没有用

同一个起点（`fixtures/todo-cli`，7 个节点、91 个测试），同一组任务（`tasks.json`），分三组条件跑同一个 agent，事后用同一套方法检查结果：

| 条件 | agent 拿到什么 | 观察者 |
| --- | --- | --- |
| 开观察者 | 节点上下文（目标、负责的文件、规则）+ 任务 | 实时检查，越界会被拦 |
| 只给节点上下文 | 同上 | 不在场，hooks 一律放行 |
| 不用 Agent Together | 只有任务原文，就像直接在 Claude Code 里打字 | 不在场 |

每次运行都在一份全新的副本里进行，结束后统计：改了哪些文件、其中哪些属于别的节点、观察者回放发现的问题（越界、违反依赖、篡改测试）、完整测试是否通过、花费和耗时。

## 运行

```bash
npm run build
node packages/hook/dist/agent-together-bench.js run bench/fixtures/todo-cli bench/tasks.json bench/results/<名字> --repeats 2 --parallel 3
```

可选：`--agent codex|cursor`、`--model <模型>`、`--only <任务id,…>`、`--conditions on,off,bare`、`--keep`（保留副本以便查看）。已经跑完的不会重跑；单独重新出报告：

```bash
node packages/hook/dist/agent-together-bench.js report bench/results/<名字>
```

## 第一次结果（2026-11-05，Claude Code + Haiku，5 个任务 × 3 组 × 2 次）

完整数据见 [results/2026-11-05-claude-haiku/report.md](results/2026-11-05-claude-haiku/report.md)。

| 条件 | 改了别的节点文件的比例 | 平均越界文件数 | 违反依赖 | 测试通过率 | 平均花费 | 平均耗时 | 观察者拦截 |
|---|---|---|---|---|---|---|---|
| 开观察者 | 0% | 0.0 | 0 | 100% | $0.014 | 84s | 0 |
| 只给节点上下文 | 0% | 0.0 | 0 | 90% | $0.013 | 83s | 0 |
| 不用 Agent Together | 80% | 3.9 | 2 | 90% | $0.020 | 113s | — |

### 结论

1. **起作用的是"计划"本身。** 只要 agent 拿到节点上下文，10 次里 0 次改别的节点的文件；不用 Agent Together 时 10 次里 8 次改了，平均 3.9 个，最多一次改了 9 个文件、出现 2 处违反依赖，并有 1 次测试失败。
2. **范围小也更省。** 有节点上下文时平均花费低约 30%，耗时短约 25%；越界最多的"软删除"任务，不用 Agent Together 时花费是 3 倍多、耗时近 3 倍。
3. **观察者这一次没有出手。** 有上下文的 20 次运行里 Haiku 全部守住了边界，观察者拦截 0 次。这次实验证明不了观察者本身的价值，只能说明它在 agent 守规矩时不添乱（花费和耗时与"只给上下文"基本相同）。
4. **没有发现篡改测试。** 三组都是 0。

### 要诚实看待的地方

- **"越界"不全是坏事。** 不用 Agent Together 时，agent 会把功能从头做到尾（比如把 `--done` 参数接到 `src/cli.ts`），用户马上就能用；有节点上下文时它只做本节点那一半，命令行入口要再派给"命令行入口"节点。这正是计划要的分工，但也意味着跨节点的功能必须在画布上拆成多个节点任务，或者靠"交给负责节点"串起来。
- **样本小。** 每组 10 次、一个模型、一个小项目。
- **任务对 Haiku 来说不够难。** 观察者的价值要在 agent 不守规矩时才看得出来。

### 下一步

- 用不太听指令的 agent（Codex、Cursor）和更有诱惑的任务（例如明确要求"顺便把相关的地方都改好"、测试本身有错）再跑，检验观察者在"计划没管住"时能不能兜住。
- 加一项"功能是否端到端可用"的检查，衡量分节点做事的完成度代价。
